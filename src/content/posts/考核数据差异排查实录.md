"你们系统算的数不对。"

这句话经常听到。一开始特别被动，只能对着客户的 Excel 一条条手算给人看，算完人家还半信半疑。

后来我把排查过程固定成一条路径，效率高多了，关系也慢慢处过来了。

## 先说个可能不太好听的前提

差异是必然的。

系统和手工表对不上，多数情况下是正常的，问题在于这个差异能不能解释。我见过的来源大概这几类：

取数时点不同，系统取的是 T 日快照，手工表是第二天上午导的。源系统后来补录了业绩，我们还没同步。口径不一致，比如"日均"到底按自然日还是按工作日。机构撤并了，人员归属没更新。精度和舍入，系统保留两位，Excel 按默认显示。还有就是手工表公式拉错了范围——这条我遇到的最多。

所以别预设是系统错。有好几次最后查出来是客户的表格把上面几行也框进去了。

## 把一句话拆成五段

客户说"数不对"是个结论，没法直接查。我会当场把它拆开：口径、源数据、抽取时点、计算过程、分配规则。然后一段一段过。

拆开讲还有个好处，客户的注意力从"你们的错"变成"我们一起看哪一段有问题"，气氛会缓下来。

先说口径。定义得落到文字上，日均存款是余额的日均还是增量的日均，分母是自然日还是工作日，节假日算不算。这一步能消掉不少争议，因为口径不清的时候，讨论对错本身没意义。

然后是源数据。系统里的原始数据和客户从源系统导出的比，先比总量再比明细：

```sql
select org_code, sum(biz_amount) as amt, count(*) as cnt
from biz_detail
where stat_date between date '2024-08-01' and date '2024-08-31'
group by org_code
order by org_code;
```

总量对得上，问题在计算；总量对不上，问题在抽取。

抽取时点这段最容易被忽略，也最容易看着像 bug。源系统在跑批，我们的抽取也在跑，两边抢时间。客户上午十点导的表，我们凌晨两点抽的数据，中间发生的补录、撤销必然造成差异。

我的处理是在系统里打取数快照标记，报表上直接显示"数据截至时间"。客户看到时间戳，很多疑问自己就解开了。

再往下是计算过程。把一条数据从原始值到最终得分的每一步打出来。

```sql
select person_code, index_code, base_value, weight,
       score_rule, final_score, calc_time
from index_score_detail
where period_id = '202408' and person_code = :person
order by index_code;
```

关键是中间值要落表，不能只存最终得分。只存结果的话，每次核对都要重算一遍，等于把成本推给未来。

最后一环是分配规则。结果到个人还有一层二次分配，机构总盘、岗位系数、封顶保底，任何一处配置不一样结果就不一样。这一步我直接把配置打印出来给客户看，比解释一堆公式有效。

## 一次印象比较深的

某支行说同一个人的绩效得分，系统比手工表低了一点。

按五步走。口径一致。源数据总量一致。抽取时点这里对不上了——客户手工表里包含了月中一次补录的业绩，我们的增量任务只扫了主表，补录表压根没纳入。计算过程因为源数据缺一块，得分自然低。分配规则无关。

根因是抽取任务漏了一张补录表。这表业务量很小，一年也没几条记录，上线时就没被纳入。

修复很简单，但如果没有前面那套拆解，光看"分数低"这个现象，很容易往计算逻辑上去查，越查越远。

## 后来做了三件事

一是增量校验任务，每天跑一次总量比对，差异超阈值就告警。

```sql
select s.org_code,
       s.amt as sys_amt,
       r.amt as src_amt,
       s.amt - r.amt as diff
from sys_daily_sum s
join src_daily_sum r
  on s.org_code = r.org_code and s.stat_date = r.stat_date
where abs(s.amt - r.amt) > 0.01;
```

二是 T+1 对账报表，给客户一张能直接看的东西，标明每个机构的系统数、源系统数、差异和原因分类。把被动解释变成主动摆出来，这个对客户关系帮助挺大。

三是核对留痕。每次客户质疑，记一条：现象、拆解结论、根因、修复方式。半年下来这份记录自己就成了最好的交付材料。

## 几句实话

不要急着说"我查一下"。先说框架——"我们按口径、取数、计算、分配四步对一遍"。客户听到结构化的回答，情绪先降一半。

用数据说话，别用形容词。"差一点点"不如"差 0.01，是舍入方式不同"。

没查清就说没查清，给个时间点。硬解释一次，信用要修很久。

数据核对这事，说到底不是技术活，是把模糊的争议变成能验证的命题。做到了，客户就不太会说"你们算错了"，而是会问"这里为什么这么算"。
